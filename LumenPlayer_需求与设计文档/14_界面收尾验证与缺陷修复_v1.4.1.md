> 自动化点击在环境里被限制，建议下轮由人工点一次确认」。
> 本轮把这条尾巴收口，并在补做验证的过程中又发现并修掉 9 个界面/构建缺陷。

## 一、为什么上一轮截不到图

`--wid` 嵌入后，mpv 的子窗口吞掉全部键鼠输入；父窗口靠子类化转发消息才能收到点击。
上一轮的自动化脚本用 `SendMessage` 发坐标，又被 DPI 虚拟化二次缩放，点到视频区去了。
在受限环境里「启动 → 点一下 → 截图」这条链一直串不起来。

本轮换了一条路：**不依赖 GUI 自动化框架，直接用 Python + ctypes 注入消息**，
并用 `Pillow.ImageGrab` 按「客户区原点 + 客户区尺寸」裁剪截图。新增工具：

```
tools/ui_probe.py
```

能力：

| 参数 | 作用 |
|---|---|
| `--exe` | 指定要启动的 exe（开发版 / 单文件发布版都可以） |
| `--media` | 启动时直接播放的文件 |
| `--scene menu / gear / play / sidebar` | 内置场景：右键菜单、点齿轮、点播放、纯截图 |
| `--click / --rclick` | 客户区坐标单击 / 右键（PostMessage，不进菜单模态循环） |
| `--realclick` | 注入**真实鼠标事件**（`mouse_event`），能打到弹出菜单上 |
| `--keys` | 注入**真实键盘事件**（`keybd_event`），能驱动菜单键盘导航 |
| `--hover` | 移动真实光标并等待 |
| `--shot` | 截图文件名，输出到 `build/shots/` |

三个必须写进工具里的知识点：

1. **坐标必须用「客户区像素」，且 PostMessage 不走 DPI 虚拟化**——探针自己要
   `SetProcessDPIAware()`，否则坐标会被系统再缩放一次。
2. **截图要截客户区，不是窗口矩形**。截 `GetWindowRect` 会把 8px 的隐形调整边框算进来，
   边缘露出底下的桌面，看起来像「界面渲染坏了」；正确做法是
   `ClientToScreen(0,0)` 取原点 + `GetClientRect` 取宽高。
3. **菜单弹出后 `TrackPopupMenu` 进入自己的模态消息循环**：`PostMessage` 到主窗口的
   鼠标/按键根本到不了菜单，必须用 `mouse_event` / `keybd_event` 注入到硬件输入队列。
   另外单击触发同步模态菜单时，排在队列里的 `WM_LBUTTONUP` 会被菜单当成「在某项上松开」
   而误选命令（本轮就误触了「打开文件…」）——所以菜单验证走右键路径或真实点击。

还有两个坑属于工具自身，不影响产品，但会毁掉证据：

- `SetForegroundWindow` 在进程刚启动时常因前台锁失败 → 截图里是上一个应用，
  只有 TOPMOST 的性能浮层孤零零飘着。修法：探针期间用 `HWND_TOPMOST` 临时置顶。
- 曾试图用「最小化再恢复」绕过前台锁，结果触发窗口尺寸变化，mpv 子窗口来不及重排，
  整个客户区被视频铺满、侧栏和控制条消失。已改回温和置前（`SW_RESTORE` + `HWND_TOPMOST`）。
- 齿轮按钮坐标第一版算漏了一个按钮宽度（用了 `px(52)`，实际是 `px(88)`），
  点到了全屏按钮。按 `player_ui.cpp` 的 `ComputeControlGeom` 逐项累加才对上。

## 三、本轮修复的缺陷（都是截图里肉眼看到的，不是猜的）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 浮层文字直接压在彩色测试图上，**宣称的半透明底衬整块消失** | `CreateDIBSection` + 直接改写 `bits` 属于「绕过 GDI 写内存」，而 `UpdateLayeredWindow` 是 GDI 调用；GDI 批处理队列没冲刷，ULW 读到的是缓存里的旧位图——只有 GDI 画过的字形能出现，手写的 alpha 底色全部丢失 | 循环写完 DIB 后、ULW 之前加 `GdiFlush()`。详见第四节 |
| 2 | 菜单项 `切换场序（tff / bff / 自动）` | 直接把内部枚举名写进 UI | 改成动态显示当前值的 `场序：自动（点击切换）`，值取自已有的 `FieldOrderZh()` |
| 3 | 菜单项 `处理开 / 原片`、`性能 HUD` | 内部简称 / 英文缩写外泄 | `画面处理效果（关掉看原片）`（带勾选）、`性能浮层`；菜单 / OSD / 帮助文本三处同步 |
| 4 | 帮助文本 `\ 恢复 1.0x` | 英文倍率写法 | `恢复 1 倍速`；`I HUD` → `I 性能浮层` |
| 5 | 浮层 `片源 720x480 d3d11 D3D11 硬解` | 硬解时 mpv 的 `pixelformat` 报的是后端名 `d3d11`，和后面的「硬解」重复且是英文；软解时则是 `yuv420p` 这类内部名 | 新增 `PixelFormatZh()`：`yuv420p → YUV 4:2:0 8 位`、`p010 → P010 4:2:0 10 位`、`yuvj* → …（全范围）`；硬解后端名直接返回空串，调用处省略该段。同时 `%dx%d` → `%d×%d` |
| 6 | 浮层 `29.97 fps 丢帧 0（解码 0）` | 「解码」和「丢帧」读起来像同一件事重复 | `29.97 帧/秒 丢帧 0（解码层 0）`；侧栏帧率单位同步改「帧/秒」 |
| 7 | 侧栏顶部 `正在播放` 与状态行 `正在播放` 上下重复 | 栏目名和状态用了同一个词 | 栏目名固定为「当前文件」，彩色状态行保留播放中 / 已暂停 / 播放结束 |
| 8 | 速度菜单把 `0.75` 写成「0.8 倍速」、`1.25` 写成「1.2/1.3 倍速」 | `swprintf(L"%.1f")` 把两位小数的档位四舍五入，标签与实际设给 mpv 的值不符 | 按分值是否为 10 的倍数选 `%.1f` / `%.2f`；最终为 `0.5 · 0.75 · 1.0 · 1.25 · 1.5 · 2.0 倍速` |
| 9 | `build.bat` 双击运行报 `'yer.exe' is not recognized` / `The system cannot find the path specified`，结尾 echo 被拆成命令执行 | 三个叠加问题：① 文件是 LF 行尾，cmd 批处理解析脆弱；② 文件是 UTF-8 中文，却在文件内部 `chcp 65001`——**chcp 对已经在解析中的 .bat 不起作用**，cmd 仍按 GBK 逐字节读，中文的某个字节被当成 `\` / `&` 把命令行截断 | 重写为**纯 ASCII**（注释与输出全英文）+ CRLF。构建脚本不是产品界面，纯 ASCII 彻底消除这一类编码坑；播放器界面仍全中文 |

## 四、最值得记的一条：`GdiFlush()`

现象非常具有迷惑性：文字在、底色不在。第一反应是「alpha 值太小」，
把 `kPanelAlpha` 从 156 改成 255（完全不透明）后**底色依旧不出现**，
才排除了「合成时被压暗」这个方向。

结论：`CreateDIBSection` 返回的 `bits` 是我们直接 `memset`、直接逐像素写 alpha 的；
而 `FillRect` / `DrawTextW` / `UpdateLayeredWindow` 都走 GDI。GDI 有批处理队列，
直接改内存与 GDI 读取混用时必须显式冲刷：

```cpp
// 直接改写 bits 之后：
GdiFlush();
// 再调用 UpdateLayeredWindow(...)
```

修复后浮层恢复为「深色半透明底衬 + 白色抗锯齿文字」，压在纯白/纯青的测试图上也能读。
**判据**：把底色 alpha 设为 255 仍看不到底色，就说明不是数值问题，而是数据根本没被 GDI 读到。

## 五、顺带重建的测试素材

原 `testdata/` 在 v1.3 清理后为空。本轮用 ffmpeg 重建 `SD_480i_30s.mkv`。
第一版用 `-flags +ildct+ilme -x264-params tff=1` 直接编码 29.97p 的 `testsrc`，
`ffprobe` 显示 `field_order=progressive`、两场来自同一帧（无场间运动），
`lumen-probe` 判定逐行是**正确**的——这是 fixture 不对，不是分析器不对。

改成先生成 59.94fps 素材、再 `tinterlace=interleave_top` 合成真正的隔行场：

```bat
ffmpeg -f lavfi -i "testsrc2=size=720x480:rate=60000/1001:duration=30" ^
       -f lavfi -i "sine=frequency=440:duration=30" ^
       -vf "tinterlace=interleave_top" -c:v libx264 -pix_fmt yuv420p ^
       -flags +ildct+ilme -x264-params "tff=1" -c:a aac -shortest ^
       testdata/SD_480i_30s.mkv
```

复核：`field_order=tb`、帧标记 `interlaced_frame=1, top_field_first=1`；
`lumen-probe` 判定 **interlaced / 置信度 100% / TFF**，处理链为
`deinterlace（场序 tff）+ bt601→bt709 矩阵转换`。播放器侧栏也如实显示
「隔行·上场优先（自动）」「反交错（上场优先）」。

> 教训：**验证素材本身也要验证**。用「看起来像隔行」的片源去验收反交错，
> 会把分析器的正确判定误当成 bug。

## 七、仍遗留

1. **实时 AI 超分未接入**：输出分辨率仍是 lanczos 缩放，侧栏与浮层如实标注「未接入」。

3. **跨盘 / 改名后旧进度条目没有清理策略**。
4. **菜单项只验证了「能展开 + 勾选正确 + 命令入口存在」**，未逐项点击后量窗口像素
   （150% / 200% / 裁剪填满 / 2160p 的实际画面变化），属于下一轮可补的端到端验证。
