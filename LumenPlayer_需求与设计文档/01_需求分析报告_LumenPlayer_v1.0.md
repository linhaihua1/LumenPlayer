## 0. 需求原文与解构结论

**用户原话**：开发一个播放器，先支持 Windows，后续支持安卓和鸿蒙；把 90—00 年代的电影电视剧从 480p / 720p 低分辨率，通过播放器自动转换为 1080p 蓝光高清。

**解构结论（一句话）**：这是一个「播放器外壳 + 实时 AI 超分渲染管线 + 老片源修复前置处理」的三合一产品，播放器本身是成熟工程量，真正的壁垒和风险全部集中在**实时超分的性能预算、老片源特有的画质缺陷处理、以及"能不能真的看起来像蓝光"的预期管理**上。

### 0.1 需求中的 5 个必须澄清的模糊点

| # | 原话 | 问题 | 本文档的裁决（待用户确认） |
|---|------|------|--------------------------|
| Q1 | "自动转换" | 是播放时实时增强，还是导出一个新文件？ | **双形态**：默认「实时播放增强」（零等待），另提供「离线重制导出」（占用后台，产物可分发/收藏）。二者共用同一套模型与策略 |
| Q2 | "1080p 蓝光高清" | 480p 片源上采样到 1080p 不可能"等于"真蓝光（真蓝光来自 35mm 胶片扫描）。该表述是技术承诺还是观感描述？ | **定位为观感目标**，对外口径统一为「蓝光级观感增强」，并在产品内提供"效果上限说明"。承诺可验收的是：无新增伪影、清晰度与信噪比可量化提升 |
| Q3 | "90—00 年代影视" | 这批片源的共性缺陷未定义：隔行/胶转磁、胶片颗粒、MPEG-2 块效应、4:3 黑边、PAL 25fps 加速 | **新增「片源自检」必需能力**（P0），自动识别并匹配处理链，不做"一套模型套所有片" |
| Q4 | "自动" | 自动到什么程度？用户是否需要干预？ | 三级自动化：全自动（默认，按自检结果选档）→ 档位手动覆盖（性能/均衡/画质）→ 高级参数（去噪强度、颗粒保留、模型链）。**默认路径零配置** |
| Q5 | 跨平台 | 安卓/鸿蒙是重写还是复用？ | **核心引擎 C++ 单一代码库 + 平台层分离**，UI 各平台原生。鸿蒙列为一期后的独立 POC 里程碑（工具链风险最高） |

## 1. 【业务全景图】

> **一句话**：LumenPlayer 让用户把家里那堆 480p/720p 的九十年代老电影、老剧集，在**按下播放键的瞬间**就呈现出接近蓝光的干净与锐利 —— 不需要懂参数、不需要等渲染、不需要换片源。
>
> **核心价值三层**：
> 1. **零等待**（实时）—— 区别于 Video2X / Topaz 这类"处理几小时才出一个文件"的工具，这是本产品的第一差异化。
> 2. **懂老片**（领域知识）—— 隔行、颗粒、块效应、色域错标，这批片源的坑是通用超分模型处理不好的，产品把这些做成自动策略。
> 3. **可解释**（信任）—— 一键 A/B 分屏对比、实时性能 HUD，让用户看见"增强了什么、代价是什么"，而不是黑盒玄学。

### 1.1 角色与权限

| 角色 | 场景 | 权限边界 |
|------|------|----------|
| 普通用户 | 双击文件即看，不关心技术细节 | 只能操作播放、档位切换、A/B 对比；看不到模型/推理后端等内部参数 |
| 进阶用户（影迷/收藏党） | 关注颗粒保留、色域、导出参数 | 可开高级面板、自定义预设、批量导出队列 |
| 系统（自动决策体） | 自检 → 选档 → 降级 | 可自主切换处理链，但必须把决策**明示**在 HUD 与日志中（不可静默降质） |
| 硬件能力（外部约束） | GPU 解码器/推理算力/显存 | 不满足时触发降级链，不可拒绝启动播放 |

> ⚠️ 本产品**无多用户、无账号、无云端权限模型**（一期纯本地单机）。这是有意的范围裁剪，可省掉整套鉴权/越权测试面。

### 1.2 对存量业务的侵入性

- 无存量系统，绿地项目。
- 唯一"外部依赖"是用户本地媒体文件：**只读**，绝不改动原文件（含不写入源目录、不重命名、不改元数据，除非用户显式选择"导出"到指定目录）。
- 一期不引入服务端、不做遥测上报（若后续加，须单独过隐私评审）。

## 2. 【逻辑与状态机】

### 2.1 播放会话状态机（核心对象：PlaybackSession）

| 当前状态 | 可迁移至 | 触发条件 | 说明 |
|----------|----------|----------|------|
| Idle 空闲 | Probing 探测 | 用户打开文件/拖入/命令行参数 | — |
| Probing 探测 | Analyzing 自检 | 容器与流信息解析成功 | 解封装 + 取首帧 |
| Probing | Failed 失败 | 格式不支持/文件损坏/无权限 | 错误码需可区分（见 3.1） |
| Analyzing 自检 | Ready 就绪 | 完成分辨率/隔行/颗粒/色域/帧率检测 | 产出 `SourceProfile` 决策输入 |
| Analyzing | Ready（降级） | 自检超时（>800ms） | 用保守默认策略，HUD 标注"自检超时" |
| Ready | Playing 播放中 | 用户播放 / 自动播放 | 首帧须 ≤1.5s |
| Playing | Paused 暂停 | 暂停键/失焦策略 | 保留最后一帧增强结果 |
| Playing | Seeking 跳转中 | 拖动进度条/快捷键 | **关键态**：超分引擎在此态最易崩 |
| Seeking | Playing | 目标帧解码 + 推理完成 | 允许丢帧但不能花屏/黑屏 |
| Playing | Degraded 降级播放 | 推理超时/显存不足/驱动重置 | 自动切 shader 超分，**不中断播放** |
| Degraded | Playing | 压力恢复（连续 N 帧达标） | 需带迟滞，防抖动式反复切换 |
| Playing/Paused | Ended 结束 | 播放到 EOF | 保留进度 |
| 任意 | Closed 已关闭 | 关闭窗口/切片 | 释放 GPU 资源（**泄漏高发点**） |
| Failed | Closed | 用户确认 | 不可从 Failed 直接回 Playing，须重新 Probing |

**非法迁移（必须被代码与测试显式拦住）**
- `Closed → Playing`：资源已释放，禁止复用 session 对象。
- `Seeking → Degraded`：跳转期间不允许触发降级判定（否则大量误降级）。
- `Ended → Playing` 非重播路径：必须先回 `Ready`。

### 2.2 超分引擎状态机（对象：EnhanceEngine）

| 当前状态 | 可迁移至 | 条件 |
|----------|----------|------|
| Uninitialized | Warming 预热 | 选定模型 + 后端（TensorRT / DirectML / CPU） |
| Warming | Active 生效 | 预热完成（首次 TensorRT 建 engine 可能耗时 10—60s，需进度提示，**不能表现为卡死**） |
| Warming | Unavailable 不可用 | 后端初始化失败/驱动不支持/显存不足 |
| Active | Bypass 旁路 | 用户关闭增强 / 片源已是 1080p+ / 电池模式 |
| Active | Fallback 降级 | 单帧推理超时 或 连续掉帧超阈值 |
| Fallback | Active | 压力恢复且通过迟滞判定 |
| 任意 | Disposed | 切片/关窗 |

**关键约束**：`Warming` 是**首次播放才暴露**的长耗时态。若不设计进度反馈，用户会认为"播放器卡住了"——这是必然会被投诉的点。

### 2.3 导出任务状态机（对象：ExportJob，P1）

| 当前状态 | 可迁移至 | 条件 |
|----------|----------|------|
| Queued 排队 | Preflight 预检 | 调度器取到任务 |
| Preflight | Running 处理中 | 目标路径可写 + 磁盘空间充足（预估产物大小 ×1.2） |
| Preflight | Rejected 拒绝 | 磁盘不足/路径冲突/源文件不可读 |
| Running | Paused 暂停 | 用户暂停 / 系统休眠 |
| Paused | Running | 用户恢复 |
| Running | Completed 完成 | 全帧处理 + 封装校验通过 |
| Running | Failed 失败 | 编码器崩溃/磁盘写失败 |
| Failed | Running | 断点续跑（**须支持，3 小时片子不能白跑**） |
| 任意（非 Completed） | Canceled 已取消 | 用户取消，须清理半成品文件 |

**孤儿状态风险**：`Paused` 状态下进程被强杀 → 重启后任务应回到 `Paused` 或 `Queued`，不得停留在"处理中"假象（僵尸任务）。

## 3. 【深度测试点】

### 3.1 架构级关注

**A. 渲染与推理管线契约**

| 测试点 | 判定标准 |
|--------|----------|
| 解码 → 推理 → 呈现 三段队列的背压 | 队列不得无界增长；下游慢时上游必须丢帧而非堆内存 |
| 推理输出与显示帧的**时间戳对齐** | 音画不同步 ≤ 40ms；不得出现"增强帧错位一帧"（画面比声音早/晚一帧） |
| GPU 资源隔离 | 解码器与推理共用 GPU 时，解码不得被饿死；1080p 播放时 GPU 总占用留 ≥20% 余量 |
| Windows TDR（默认 2s） | 单帧推理超 2s 会触发驱动重置导致**整机黑屏闪烁**。须限制每帧推理切片粒度，且捕获设备移除/重置事件后能自愈 |
| TensorRT engine 缓存 | 缓存键须含 GPU 型号 + 驱动版本 + 模型哈希；换卡后不得误用旧 engine（否则崩溃） |
| 显存峰值 | 1080p 输出 + 3 帧缓冲 + 模型 ≤ 2GB（保证 4GB 显存入門卡可用） |

**B. 数据一致性 / 幂等**

| 测试点 | 判定标准 |
|--------|----------|
| 同一文件重复打开 | 不产生重复缓存条目；不重复解压模型 |
| 同一导出任务重复提交 | 幂等键 = 源文件路径 + 大小 + mtime + 预设；重复进入不得生成两份产物 |
| 进度记忆 | 播放进度、档位、每片自检结果持久化；崩溃后恢复不串片（多片进度不得互相覆盖） |
| 配置与缓存版本 | 升级后旧配置须可迁移，不得因新增字段导致启动即崩（兼容性硬要求） |
| 中断续跑 | 断点帧号 + 编码器状态一致；续跑后产物不得出现重复帧或音画偏移累积 |

**C. 存储与 I/O**

| 测试点 | 判定标准 |
|--------|----------|
| 网络盘（SMB/NAS）播放 | 大缓冲场景不卡顿；断连后给出明确提示而非无限转圈 |
| 超长路径 / 中文 / emoji 文件名 | Windows 260 字符限制、非 ASCII 路径必须正常（**历史高频缺陷**） |
| 只读介质（光盘镜像、只读目录） | 播放正常；不得尝试写源目录 |
| 磁盘缓存上限 | 缓存可设上限并可清理；不得无上限蚕食 C 盘 |

### 3.2 业务级关注

**A. Happy Path（按 90—00 年代真实片源类型分条）**

| 片源类型 | 典型特征 | 期望行为 |
|----------|----------|----------|
| DVD 480i（NTSC 影视剧） | 隔行、3:2 pulldown | 自动 IVTC 还原 24fps 后再超分，**不得对隔行帧直接推理**（会放大梳齿） |
| DVD 576i（PAL 剧集） | 25fps、4% 加速、音调偏高 | 去隔行 + 可选 25→24 变速（含音频同步变调），默认仅画面处理不擅自改音频 |
| 720p 网络片源（早期压缩） | 块效应、色带、蚊噪 | 轻去块 + 轻度去噪 + 2x 内插到 1080p，禁止重去噪（会糊） |
| 4:3 老片 / 变形宽银幕 DVD | 黑边、anamorphic 标记 | 正确识别 AR，**不得把黑边当画面内容放大**（导致画面被压扁/出现黑边套黑边） |
| 动画（90 年代赛璐璐） | 平涂色块 + 硬边 | 应切换到动画专用链；通用实景模型会给平涂区加假纹理 |
| 已带字幕烧录（硬字幕） | 字幕在画面内 | 超分不得使字幕边缘出现光晕/锯齿加剧；须用带文本保护的模型或降低锐化 |

**B. 边界值**

- 分辨率边界：320×240（VCD）→ 720×576 → 1920×1080 → 4K 源（应自动旁路，不做无意义放大）。
- 帧率边界：15fps（早期动画）／23.976／25／29.97／60fps；变帧率（VFR）片源。
- 时长边界：30 秒短片 → 3 小时长片 → 10 小时连续播放（马拉松）。
- 码率边界：300kbps 极低码率（几乎全是块）→ 40Mbps 高码率。
- 音轨边界：无音轨 / 单声道 AC3 / 5.1 / 多音轨切换 / DTS 直通。

**C. 逆向与异常**

| 场景 | 期望行为 |
|------|----------|
| 用户中途关闭超分 | 立即切回原始渲染，不黑屏、不卡顿、进度不跳 |
| 播放中拔掉独显 / 切到核显（笔记本） | 降级到 CPU 或 shader 路径，播放继续 |
| 播放中 GPU 驱动崩溃（TDR） | 自动重建后端；连续 3 次失败则本次会话永久降级并提示 |
| 显存不足（同时开游戏/浏览器） | 降档而非崩溃；须有显存申请失败兜底 |
| 文件被其他进程占用/边下边播（不完整文件） | 明确提示"文件不完整"，不静默黑屏 |
| 导出中拔电源/断电 | 重启后可续跑，提示上次中断位置 |
| 用户把 1080p 片源强行开到"画质"档 | 允许但提示"无增益"，避免算力浪费与过度锐化 |

### 3.3 性能 / 安全 / 合规关注

**A. 性能基线（一期硬指标，须进 CI 门禁）**

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 首帧时间（1080p 输出，含预热缓存命中） | ≤ 1.5s | 冷启动首次含 engine 构建不计入，但须有进度 UI |
| 稳态帧率 | 输出 24/30fps 片源 **不丢帧** | 单帧预算：24fps≈41ms、30fps≈33ms，**留 30% 余量 → 模型推理须 ≤28ms/帧** |
| 掉帧率 | < 0.5% / 10 分钟 | HUD 实时可查 |
| 音画同步漂移 | < 40ms（3 小时累计） | 不得随时间累积 |
| 内存 | 常驻 < 1.5GB（1080p 输出） | 3 小时播放后不得持续增长（泄漏门禁） |
| CPU 占用 | < 25%（4 核，硬解路径） | — |
| 启动时间 | ≤ 3s（冷启动到可交互） | — |
| 功耗 | 笔记本电池模式自动降档 | 避免"看一集掉 40% 电" |

**B. 画质客观指标（把"像蓝光"变成可测量的东西）**

| 指标 | 方法 | 验收 |
|------|------|------|
| 无新增伪影 | 人工盲测 + 静态帧评审（≥5 人，含 2 名影视从业） | 不得出现蜡像脸、塑料皮肤、振铃、光晕、纹理蠕动（texture crawling） |
| 颗粒保真 | 与原片颗粒能量谱对比 | 默认档颗粒保留率 60%—80%，不得把胶片颗粒抹成"水磨皮" |
| 锐度提升 | 边缘锐度/MTF 代理指标 | 相对原片提升 ≥25%，且不伴随锯齿 |
| 时序稳定性 | 连续帧差分抖动 | 静态场景不得出现逐帧闪烁/呼吸感 |
| 色域正确性 | BT.601/709 标记校验（肤色/天空色块） | 不得整体偏绿/偏红；老片 SD 内容须按 601 解码后再转 709 |
| 黑位与色带 | 渐变色带测试图 | 10bit 输出路径下色带不加重 |

**C. 安全与合规**

| 风险 | 要求 |
|------|------|
| 内容版权 | **播放器不提供、不索引、不下载任何片源**；仅播放用户本地文件；不实现 DRM 破解/解密；EULA 明示用户须对内容合法性负责 |
| 模型与代码许可 | 主程序不得链接 AGPL 组件（如 Video2X）；FFmpeg 须用 LGPL 配置（**禁用 libx264/libx265 等 GPL 编码器**，导出走硬件编码器） |
| 文件安全 | 解析第三方媒体文件属于高危攻击面（畸形 MKV/AVI），须做 fuzz 与沙箱化降权；不执行容器内任何脚本/外链 |
| 隐私 | 一期不上传任何数据；若后续加崩溃上报，须脱敏且可关闭 |
| 供应链 | 模型文件须锁定哈希与来源，防止被替换（模型即代码） |

## 4. 【风险建议/缺陷预警】

### 4.1 需求层面（建议需求澄清）

| # | 风险/缺陷预警 | 优先级 | 归属 |
|---|--------------|--------|------|
| R1 | **"1080p 蓝光高清"是不可兑现的技术承诺**。480p 上采样只能"看起来更干净锐利"，不可能还原从未被记录的信息。若对外这样宣传，必然产生大量"没变蓝光啊"的退款/差评。建议口径改为「蓝光级观感」，并在产品内提供"增强上限说明 + 前后对比"。 | 高 | 需求澄清（对外表述） |
| R2 | **"自动转换"的形态未定**，实时与离线是两套完全不同的工程量与体验（实时=管线/同步/掉帧；离线=队列/续跑/封装/编码）。建议明确为"实时为主、离线为辅"，否则一期范围会失控翻倍。 | 高 | 需求澄清 |
| R3 | 未定义**片源缺陷处理策略**。90—00 年代片源的头号杀手不是分辨率低，而是隔行、胶转磁、块效应、色域错标。若只做"超分"，结果会是"放大的糊 + 放大的锯齿"。建议把「片源自检 + 预处理链」列为 P0，而非后期优化。 | 高 | 设计补充 |
| R4 | 未定义**低端硬件的行为**。大量用户是核显笔记本。若无"无独显也能用"的降级链（shader/传统上采样），会出现"装了打不开/一播就卡死"的致命口碑问题。 | 高 | 设计补充 |
| R5 | 未定义**"颗粒"的产品立场**。AI 去噪 + 超分默认会把胶片颗粒抹平，观感是"高清但假"。影迷群体对此极度敏感。建议把"颗粒保留强度"做成显性可调项，并默认偏保守。 | 中 | 需求澄清 |

### 4.2 技术层面（建议研发前置验证）

| # | 风险/缺陷预警 | 优先级 | 归属 |
|---|--------------|--------|------|
| R6 | **实时推理与解码抢 GPU**。480p→1080p 单帧推理在入门独显上可能刚好卡在 30—50ms，一旦超预算就必然掉帧。**必须在写播放器之前先做"纯推理性能探针"**（POC-0），用真实老片片段测各档模型在目标显卡上的 ms/帧，否则架构选型全是猜。 | 高 | 测试重点关注（前置POC） |
| R7 | **首次 TensorRT 建 engine 耗时数十秒**，若直接塞进播放流程会表现为"打不开"。须设计：进度提示 + 后台预热 + 预置通用 engine + 失败兜底到 DirectML。 | 高 | 设计补充 |
| R8 | **TDR 风险**：Windows 显卡超时检测（默认 2s）会因单帧推理过长重置驱动，表现为整屏黑闪甚至播放器进程被杀。须分块推理 + 捕获设备重置 + 自愈重建。 | 中 | 测试重点关注 |
| R9 | **跨平台推理后端不统一**。Windows 有 TensorRT/DirectML；Android 有 NNAPI/QNN/Vulkan(NCNN)；**HarmonyOS NEXT 的推理链路成熟度与算子覆盖是最大未知数**。若架构把推理写死在 Windows API 上，二三期等于重写。建议核心层抽象 `IInferenceBackend`，并在 M2 就做鸿蒙最小 POC（单帧推理能否跑通）。 | 高 | 设计补充 |
| R10 | **开源许可传染**。Reference 类工具（Video2X 为 AGPL-3.0）若被"参考"进代码库，闭源分发即违规。FFmpeg 默认构建常带 GPL 编码器。须在工程规范里锁死依赖白名单。 | 高 | 需求澄清（法务） |
| R11 | **长时播放资源泄漏**。3 小时播放 + 频繁 seek 是 GPU 句柄/纹理/解码器实例泄漏的标准暴露场景，且只在长跑中显现。须把"3 小时连续播放 + 200 次 seek"纳入每轮回归。 | 中 | 测试重点关注 |
| R12 | **可观测性缺失**。超分是黑盒，出问题时无法定位是"模型不行/后端没生效/解码出的帧本身就坏"。必须内置 HUD（后端、模型、ms/帧、丢帧、当前处理链）+ 可导出诊断包。 | 中 | 设计补充 |

### 4.3 专家 Checklist 自查结论

| 维度 | 结论 |
|------|------|
| **幂等性** | 存在三处风险：重复导出、重复打开同片、重复触发后端初始化。均需幂等键 + 单例保护。**不通过，需在 PRD 中显式约束。** |
| **一致性** | 无分布式系统，但存在"配置/缓存/engine 缓存"三份本地状态的版本一致性；升级迁移必须可回滚。**有条件通过。** |
| **兼容性** | 高危：Windows 10/11 × N 卡/A 卡/Intel 核显/Arc × 驱动版本组合爆炸；老片容器格式（RMVB/WMV/AVI）解析兼容性。**需建立硬件矩阵与格式矩阵。** |
| **可观测性** | 当前需求完全未提，但超分产品没有 HUD 与诊断包等于不可维护。**不通过，已列为 P0。** |

## 5. 结论与下一步

1. 需求可做，但**必须先纠正两件事**：把"蓝光"从技术承诺降级为观感目标；把"片源自检/预处理"从加分项提为 P0。
2. 开发顺序必须倒过来：**先证明实时超分跑得动（POC-0），再做播放器**。播放器是已知工程，超分是未知风险。
3. 待用户确认的 5 个问题见 §0.1 表格；确认后本文档升 v1.1，并同步 PRD 与测试点 Checklist。
