# LumenPlayer 里程碑路线图与风险登记

| 项目 | 内容 |
|------|------|
| 版本 | v1.0 |
| 日期 | 2026-11-20 |
| 说明 | 里程碑按**能力门禁**划分，不按日历排期。每个 M 有明确"过闸标准"，未过闸不进下一个 M |

---

## 1. 路线图总览

```
M0 可行性验证  →  M1 体验原型  →  M2 核心引擎  →  M3 Windows 公测  →  M4 移动端  →  M5 鸿蒙
   POC-0/1/2        效果 Demo       自研管线+跨平台     性能/画质/稳定      Android        HarmonyOS
   ↑ 阻塞一切        ↑ 可对外演示     ↑ 架构定型          ↑ 上线门禁          复用 70%+       保底方案
```

**关键原则：M0 不过闸，不写播放器代码。** 播放器是已知工程，超分是未知风险；先证明后者。

---

## 2. 里程碑明细

### M0 — 可行性验证（阻塞闸门）

| 项 | 内容 |
|----|------|
| 目标 | 用数据回答"实时超分在我的目标硬件上跑得动吗、画质值不值得做" |
| 交付物 | ① 推理探针工具（命令行，输入片段 → 输出 ms/帧/画质对比图）② 6 类标准样本集 ③ 硬件×模型性能矩阵表 ④ 画质盲测报告 ⑤ Go/No-Go 决策单 |
| 过闸标准 | 中端独显在 30fps 片源下推理 ≤23ms；核显着色器路径 ≤10ms；盲测无"蜡像脸/振铃/纹理蠕动"；跨平台单帧推理至少 1 个非 Windows 平台跑通 |
| 未过闸的 Plan B | 产品定位改为「离线重制为主」：放弃实时播放增强，改为"导入→队列→导出 1080p 文件"，PRD §3.3 整体重写 |
| 估算 | **3—5 天**（原估 2—3 周；因上游 `aji_harness` 与公开基准可直接复用，见 06 文档 §8） |

### M1 — 体验原型（可对外演示）

| 项 | 内容 |
|----|------|
| 目标 | 做出"肉眼能看出差别"的播放器 Demo，验证价值主张与 A/B 对比体验 |
| 技术路线 | libmpv 嵌入 + 推理注入（允许走快捷方式，允许有 Python/外部进程依赖） |
| 交付物 | 可执行 Demo：打开文件 → 自动自检 → 超分播放 → A/B 分屏 → 性能 HUD |
| 过闸标准 | 6 类样本均能播放且增强生效；A/B 对比严格同帧；HUD 数值可信；演示时无崩溃 |
| 刻意不做 | 导出、字幕精调、多音轨、配置体系、安装包 |
| 估算 | **2—3 周**（原估 4—6 周；走 06 文档路线 A，复用 mpv + vf_animejanai + 现成 GUI 壳） |

### M2 — 核心引擎（架构定型）

| 项 | 内容 |
|----|------|
| 目标 | 按 06 文档选定的复用路线定型架构，为三平台铺路（路线 A/B：保留 libmpv 内核，自研策略层与推理接入；路线 C：自研管线 + 平台抽象层） |
| 交付物 | ① `IRenderer/IDecoder/IInferenceBackend/IAudioOut` 四个抽象 ② 五段式管线（场处理/几何/色彩/前置修复/超分+后处理）③ 策略引擎（自检→选链→降级）④ 帧调度与音频主时钟 ⑤ 单元测试 + 帧比对测试基线 |
| 过闸标准 | 1080p 输出稳态零丢帧（30fps 片源）；音画漂移 <40ms/3h；200 次 seek 无泄漏；TDR 自愈成功率 100%；**鸿蒙单帧推理 POC 有明确结论** |
| 估算 | 8—12 周 |

### M3 — Windows 公测（上线门禁）

| 项 | 内容 |
|----|------|
| 目标 | 可发布的 Windows 版本 |
| 交付物 | 安装包（含基础模型）、自动更新、崩溃/诊断包、完整设置体系、导出队列（P1 若资源允许）、用户文档与"效果上限说明" |
| 过闸标准 | 《02_测试点Checklist》P0 全绿；硬件矩阵抽测通过（N/A/I 三系各 ≥3 档）；3h 长跑无泄漏；fuzz 0 崩溃；许可审计通过（无 AGPL、无 GPL 编码器、零网络请求） |
| 估算 | 6—8 周 |

### M4 — Android

| 项 | 内容 |
|----|------|
| 目标 | 复用核心引擎，重做渲染（Vulkan/GLES）与解码（MediaCodec） |
| 关键挑战 | 移动端算力/发热/续航；MediaCodec Surface 零拷贝链路；机型碎片化 |
| 过闸标准 | 中高端机型（骁龙 8 系 / 天玑 9000 系）1080p 输出不丢帧且机身温度可控；中低端走降级链可用；后台/来电/旋转等生命周期正确 |
| 估算 | 8—10 周 |

### M5 — HarmonyOS NEXT

| 项 | 内容 |
|----|------|
| 目标 | 原生 HAP，ArkTS UI + NDK 渲染 + 推理后端适配 |
| 关键挑战 | 推理链路（OM 模型转换 / NCNN-Vulkan）、算子覆盖、性能未知 |
| 保底方案 | 若 AI 推理不可用 → 仅提供着色器超分（效果弱但可用），并明示 |
| 过闸标准 | 单帧推理或着色器增强跑通；真机 1080p 播放可用；过审上架 |
| 估算 | 6—10 周（不确定性最高，需在 M2 就启动技术预研） |

## 3. 风险登记表

> 等级 = 概率 × 影响。**红** = 可能推翻产品定位；**橙** = 影响里程碑；**黄** = 影响体验/口碑。

| ID | 风险 | 概率 | 影响 | 等级 | 应对措施 | 责任 |
|----|------|------|------|------|----------|------|
| R-01 | 实时推理在目标硬件上跑不进预算，产品定位失效 | 中 | 极高 | 🔴 | M0 探针前置；预留"离线重制为主"的 Plan B；档位分级到着色器 | 技术负责人 |
| R-02 | 用户预期"变真蓝光"，实际只是"更干净的放大"，口碑反噬 | 高 | 高 | 🔴 | 对外口径统一为"蓝光级观感"；产品内提供效果上限说明 + 强制 A/B 对比首体验 | 产品 |
| R-03 | 老片隔行/胶转磁处理不当，放大后更丑 | 高 | 高 | 🔴 | 场处理前置为 P0；建立 6 类标准样本集；隔离"隔行帧直接推理"的代码路径 | 算法/工程 |
| R-04 | 鸿蒙推理链路不可用或性能不合格 | 中 | 中 | 🟡 | 已有 `mpv-ohos/libmpv-ohos-build` 与生产级鸿蒙 mpv 应用，播放内核风险大幅下降；**剩余风险集中在 AI 推理**（libaji 不支持 OHOS，需另找 Vulkan/NPU 路径）。M2 做最小 POC | 架构 |
| R-05 | 过度去噪导致"蜡像脸/塑料感"，影迷群体流失 | 高 | 中高 | 🟠 | 颗粒回注 + 保留强度显性可调 + 默认保守；盲测门禁 | 算法 |
| R-06 | 开源许可违规（AGPL 传染 / GPL 编码器） | 中 | 高 | 🟠 | 依赖白名单 + CI 许可扫描 + 法务过闸；导出只走硬件编码 | 工程/法务 |
| R-07 | TDR 导致驱动重置、黑屏，被判定为"播放器把电脑搞崩了" | 中 | 中高 | 🟠 | 切片推理 + 设备丢失自愈 + 降级提示；长跑压测覆盖 | 工程 |
| R-08 | 核显用户群体体验崩塌（打不开/一播就卡） | 中高 | 中 | 🟠 | 硬件自检 + 强制降级链 + 首次启动给出"你的机器能到什么程度" | 工程/产品 |
| R-09 | 长时播放资源泄漏，只有长跑才暴露 | 中高 | 中 | 🟡 | 3h + 200 seek 纳入每轮回归；资源计数自检 | 测试 |
| R-10 | 格式兼容性缺口（RMVB/WMV/特殊 AVI）引发"打不开"差评 | 中 | 中 | 🟡 | 格式矩阵测试 + 明确的"不支持原因"提示，不静默失败 | 测试 |
| R-11 | 首次 TensorRT engine 构建被误解为卡死 | 高 | 中 | 🟡 | 进度 UI + 后台预热 + 临时兜底后端 | 工程 |
| R-12 | 24fps 内容在 60Hz 屏抖动被误认为画质问题 | 中 | 中 | 🟡 | 帧节奏控制 + HUD 显示呈现节奏 + 帮助文档说明 | 工程 |
| R-13 | 安装包因模型过大影响下载转化 | 中 | 中 | 🟡 | 基础档随包、高档按需下载 | 产品 |
| R-14 | 跨平台核心复用率不及预期，二三期成本翻倍 | 中 | 中高 | 🟠 | M2 强制落地四个抽象接口；非 Windows 平台在 M2 就跑通单帧推理 | 架构 |

## 4. 待用户决策清单（阻塞 PRD 定版）

| # | 决策点 | 选项 | 影响 |
|---|--------|------|------|
| D1 | 一期是否同时做"实时"和"离线导出"？ | A 只做实时（推荐）/ B 都要 / C 只做离线 | 直接决定工期翻倍与否 |
| D2 | 对外宣传口径 | A "蓝光级观感增强"（推荐）/ B "1080p 蓝光高清" | 决定口碑风险上限 |
| D3 | 是否闭源 / 是否收费 | 闭源收费 / 闭源免费 / 开源 | 决定许可选型（LGPL vs GPL、能否用 libmpv） |
| D4 | 目标硬件下限 | 只支持独显（体验好、用户少）/ 覆盖核显（用户多、体验分层） | 决定降级链投入与支持成本 |
| D5 | 模型分发方式 | 随包（简单、包大）/ 按需下载（包小、首启需联网） | 与"零网络请求"的合规承诺冲突，需取舍 |
| D6 | 4:3 老片默认策略 | 保留原构图（推荐）/ 自动裁黑边铺满 | 决定默认观感与"是否尊重创作"的立场 |
| **D7** | **复用路线：A 开源快速 / B 自研外壳+复用引擎（可闭源）/ C 全自研** | **✅ 已决策：A+B+C 分层结合**（A 播放内核 · B 可替换引擎 · C 自研策略层），见《07_ADR-001》 | 已定架构；W8 决策门再定"是否降级为 LGPL + 换自研后端" |
