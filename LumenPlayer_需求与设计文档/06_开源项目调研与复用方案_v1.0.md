| 项目 | 内容 |
|------|------|

## 0. 一句话结论

有一个项目几乎就是我们想要的东西 —— **`the-database` 的 `libaji`（推理引擎）+ `vf_animejanai`（mpv 视频滤镜）**：GPU 常驻 YUV 帧进、超分帧出，TensorRT / DirectML 双后端，还自带 ms/帧 基准工具。它证明了架构可行，也把我们要踩的坑全踩过了。

但它头顶三把锁：

| 组件 | 许可 | 意味着 |
|------|------|--------|
| `mpv-AnimeJaNai`（整合发行版） | **CC BY-NC-SA 4.0** | **禁止商业使用**，且必须署名 + 相同方式共享 |
| `the-database/mpv`（带 vf_animejanai 的 mpv fork） | 继承 mpv → **GPLv2+** | 一旦分发，整个程序必须开源 |
| `libaji` / `animejanai-inference` | **无 LICENSE 文件** | 默认「保留所有权利」，**不授权任何人使用**，需作者书面许可 |

所以答案是：**能复用，但先选边站。** 见 §5 三条路线。

## 2. 头号发现：libaji 的架构正好是我们 §4 想画的那张图

上游 README 的关键事实（原文摘录）：

> "`libaji` runs ONNX upscaling models, plus RIFE interpolation and temporal models, entirely on the GPU, with three backends: TensorRT and TensorRT-RTX (NVIDIA) and DirectML (Windows, any DirectX 12 GPU). Callers load it at runtime through one of two C ABIs, so they never link TensorRT."
>
> "**Video** (`include/aji.h`): GPU-resident YUV frames in, upscaled frames out, with chains, RIFE and temporal models configured by `animejanai.conf`."
>
> "Reports device-side ms/frame for the full pre+infer+post chain (**RTX 5090 reference: ~3.8 ms at 1920x1080→4K fp16**)."

这段信息价值极高，直接改写我们的三个判断：

| 我们原文档的判断 | 上游事实 | 修正 |
|------------------|----------|------|
| 「自持渲染器，自己写推理调度」是必须的（04 §2） | 上游也用**运行时动态加载**（dlopen `aji.dll`），播放器不链接 TensorRT | **架构得到验证**，且证明"MSOFT 编码的库与 mingw 编译的 mpv 可共存"这个坑已有解 |
| 单帧预算要靠 POC 测（05 M0 需 2—3 周） | 已有公开基准：1080p→4K 约 3.8ms（RTX 5090）；我们 480p→1080p 像素量只有 1/6—1/12 | **M0 可压缩到 3—5 天**，甚至直接拿 `aji_harness` 跑 |
| 模型要自己挑 | libaji 接受**任意** 1/3 通道 NCHW ONNX，整数倍率，fp16/fp32，动态或固定尺寸 | **可以直接换实景模型**，不必改引擎 |

**两个必须记住的技术细节**（README 原文）：
1. **DirectML 路径 ONNX 必须导出到 opset ≤19** —— DirectML EP 缺少 opset-20 的 `Gelu` 等算子，会回落到 CPU，"run dozens of times slower"。这是很容易踩的坑。
2. **首次 TensorRT 加载要建 engine，"minutes, once per model, tile size, GPU and TensorRT version"** —— 印证 04 §7-T1 的判断，且缓存键维度与我们设计一致。

## 3. 与现有项目的差异：我们不重复造轮子，但确实有增量

调研的残酷事实：**这些项目 95% 是"动漫 + 1080p→4K"**。

| 维度 | 现有项目 | 我们要的 | 是否自研 |
|------|----------|----------|----------|
| 内容类型 | 动漫（线条/平涂，模型专精） | **实景老电影/老剧**（皮肤、织物、胶片颗粒） | ✅ 换模型 + 调参 |
| 输入分辨率 | 1080p（画面本来就干净） | **480p/576p/480i**（糊 + 隔行 + 块效应） | ✅ 新增能力 |
| 隔行/胶转磁 | 基本不处理 | **必须先做 IVTC/去隔行**（否则放大梳齿） | ✅ **核心增量** |
| 色域 | 假定 709 | **SD 多为 601 且常被错标** | ✅ 核心增量 |
| 画幅 | 16:9 | **4:3 / 变形宽银幕 / 加黑边** | ✅ 核心增量 |
| 颗粒 | 去噪越干净越好 | **必须保留胶片颗粒**（否则蜡像脸） | ✅ 核心增量 |
| 输出 | 4K | 1080p（算力更宽裕） | 👉 有利 |

**结论**：上游给的是「推理管线 + 播放内核」这两块最贵的基建；我们要做的是「老片领域知识与策略层」。这不是重复造轮子，是补上别人没做的那一半 —— 正好也是产品差异化的来源。

## 4. 可复用度评估（按我们的模块拆）

| 我们的模块（见 PRD §3） | 可复用上游 | 复用度 | 说明 |
|------------------------|-----------|--------|------|
| 解封装/解码/字幕/音轨/seek | mpv / libmpv | **90%** | 自研这块是浪费生命 |
| GPU 渲染与呈现 | mpv `vo=gpu-next` / libplacebo | **85%** | 含 HDR tone-mapping、缩放算法 |
| 推理调度与后端 | libaji（`aji.h`） | **90%**（若许可解决） | YUV 直进直出，免去自己写 D3D11↔CUDA 互操作 |
| 超分模型 | Real-ESRGAN（BSD-3） | **80%** | 实景模型需自行挑选/微调 |
| 核显兜底 | Anime4K shader（MIT） | **95%** | 直接可用 |
| 配置器/引擎下载器 | L-MPV / AnimeJaNaiUpdater | **60%** | 硬件识别 + 分包下载 + 哈希校验逻辑可借鉴（代码许可需注意） |
| 基准工具 | `aji_harness` / `AnimeJaNaiBenchmark` | **95%** | M0 直接拿来用 |
| 片源自检（隔行/色域/AR/黑边） | 无 | **0%** | 自研，差异化所在 |
| 老片处理链策略 | 无 | **0%** | 自研 |
| 颗粒保留 | 无 | **0%** | 自研 |
| A/B 对比 / 画质 HUD | 部分（mpv 有截图/统计） | **40%** | 需改造 |
| 离线导出队列 | VideoJaNai（GPL）/ vs-mlrt | **50%** | 可参考架构，代码受 GPL 约束 |
| Android 播放壳 | mpv-android / mpvKt / mpvEx | **70%** | UI 与生命周期现成 |
| Android AI 超分 | 无（libaji 不支持 Android） | **0%** | 需 NCNN-Vulkan 或 ORT-NNAPI 另做 |
| 鸿蒙播放内核 | libmpv-ohos-build / mpv-arkts | **60%** | 有人跑通了，能省大量踩坑 |

**综合**：Windows 端若走「复用 mpv + libaji」，**整体工作量可压到原计划的 20%—35%**；Android 的 AI 超分和鸿蒙仍是硬骨头。

## 5. 三条路线（必须先选，否则代码白写）

### 路线 A：站在上游肩膀上，接受开源（最快）

- **做法**：fork `mpv-AnimeJaNai` / 直接在 `the-database/mpv` 上加自己的滤镜与策略层；UI 用现成 mpv 前端改造
- **工期**：Windows 可用版本 **2—4 周**
- **代价**：① 许可为 **CC BY-NC-SA 4.0 → 不能商用**；② 底层 mpv 是 GPL → 分发即须开源；③ 品牌与产品形态受上游限制
- **适合**：自用工具、开源项目、技术验证、内部 PoC

### 路线 B：自研外壳 + 复用引擎（可闭源，推荐给商业产品）

- **做法**：
  1. 播放内核用 **LGPL 构建的 libmpv**（`--enable-lgpl`，禁 GPL-only 组件）→ 可闭源动态链接
  2. 推理层向 libaji 作者**申请商业授权**（它无 LICENSE 文件，法律上默认保留所有权利，但作者明确以"给别人集成"为设计目标，授权谈判有基础）
  3. 若授权不成 → 自研等价层：ONNX Runtime（MIT）+ DirectML/TensorRT EP + 自己写 D3D11↔推理的零拷贝互操作（这是 04 §4 的原方案，约 6—10 周）
  4. 模型用 Real-ESRGAN（BSD-3）+ Anime4K（MIT），完全干净
- **工期**：Windows 可用版本 **8—14 周**
- **代价**：要处理 LGPL 合规（动态链接、提供替换库、附许可文本）；libaji 授权可能有费用
- **适合**：要卖钱、要品牌、要长期迭代

### 路线 C：完全自研（最干净，最慢）

- **做法**：只借模型与算法思想（BSD/MIT），播放器与推理全部自写
- **工期**：**5—8 个月**才到可用
- **代价**：把 mpv 二十年的坑（字幕、同步、格式兼容、seek 精度）重踩一遍
- **适合**：有强合规要求（如要进应用商店且不接受 LGPL）或团队想长期掌控

### 推荐

| 你的目标 | 选 |
|----------|-----|
| 先自己用 / 先验证值不值得做 | **A**（2 周见效果，不合适就停，沉没成本极低） |
| 要做产品卖钱 | **B**（A 做出来的策略层代码 80% 可迁移到 B） |
| 有严格合规/上架要求 | **C**，但先把 A 当原型验证需求 |

> **最优路径其实是 A → B**：用 A 在 2 周内把「片源自检 + 老片策略 + 颗粒保留 + A/B 对比」这套真正的差异化做出来并被验证；这套代码与许可无关，可原样搬到 B。**先花两周买确定性，再决定投不投 3 个月。**

## 7. 许可合规红线（本次调研新增，务必加进工程规范）

| # | 红线 | 说明 |
|---|------|------|
| L1 | **CC BY-NC-SA 4.0 ≠ 可商用** | `mpv-AnimeJaNai` 明确 NonCommercial。哪怕只改一行也不能商用；且 SA 要求衍生作品同协议共享 |
| L2 | **无 LICENSE 文件 ≠ 免费** | `animejanai-inference`（libaji）无许可文件，法律上默认保留所有权利。**集成前必须取得作者书面许可**，GitHub issue/邮件留痕 |
| L3 | **GPL 传染范围** | 分发基于 mpv 的二进制 → 整个作品须以 GPL 提供源码。**"我只是动态链接" 对 GPL 不成立**（那是 LGPL 的规则） |
| L4 | **LGPL 的正确用法** | libmpv 需 `--enable-lgpl` 构建；动态链接；允许用户替换库；附许可与源码获取方式 |
| L5 | **NVIDIA SDK 不可再分发** | TensorRT/CUDA 运行时受 NVIDIA 许可约束，不能打进安装包（上游 vsr-player 的做法是安装脚本从官方源下载） |
| L6 | **模型也有许可** | `2x_AnimeJaNai` 模型随 CC BY-NC-SA 仓库分发 → 同样不可商用；换 Real-ESRGAN（BSD-3）权重 |
| L7 | **"参考代码" 也算衍生** | 把 GPL/NC 项目的代码"改写"进自己项目，仍是衍生作品。只可读思路，不可抄实现 |

## 8. 本周可执行动作（研究用途，不涉及分发）

```bash
# 1) 拿基准数据（替代原 M0 的 2-3 周探针）
#    下载 animejanai-inference 的 Windows release，取 aji.dll / aji_dml / aji_trt
# 2) 抽 12 段真实老片片段（每段 30-60 秒，仅用你合法持有的素材）
ffmpeg -ss 00:05:00 -t 30 -i old_dvd.mkv -pix_fmt p010le -f rawvideo clip.raw
# 3) 跑基准，出 ms/帧
aji_harness --engine model.engine --input clip.raw --width 720 --height 480 \
            --format p010 --output out.raw
# 4) 对比：同一片段跑 Anime4K shader 路径，记录观感差异
# 5) 结论落到 05_里程碑 的 M0 决策单：走 A / B / C
```

> 本地跑基准属于研究评估，不构成分发，NC 条款不限制；**但一旦要打包给别人用，立刻受 §7 约束。**
