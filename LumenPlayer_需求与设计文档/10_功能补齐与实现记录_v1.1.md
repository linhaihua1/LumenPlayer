## 1. ONNX Runtime 超分后端

### 1.1 为什么是「动态加载」而不是「链接 SDK」

三条硬理由：

1. **构建成本**：链接方案需要下载 100+ MB 的 onnxruntime SDK，且 Windows 下还要
   对应版本的 `.lib`。当前项目"编译期零第三方依赖"的性质会被破坏，CI 与新人上手都会变复杂。
2. **部署灵活性**：用户可以把 `onnxruntime.dll` 放在模型旁边、程序旁边或任意目录
   （配置 `engine.runtime_dir`）。链接方案做不到这一点。
3. **许可与体积**：DLL 是 MIT，但如果打进安装包，我们就要跟着它升级、为它的
   CVE 负责。动态加载把"要不要装、装哪个版本"交还给用户。

实现方式：只保留官方 `onnxruntime_c_api.h`（纯声明），运行时
`LoadLibrary` + `GetProcAddress("OrtGetApiBase")`，再通过 `GetApi(version)` 拿函数表。
**不需要导入库，不产生任何链接依赖。**

### 1.2 版本协商

头文件是 1.20（API 20）。用户可能装的是 1.15、1.18……`GetApi(20)` 会返回空。
处理方式是从 20 往下退到 12，取第一个非空：

```cpp
for (uint32_t v = ORT_API_VERSION; v >= 12; --v) {
  api = api_base->GetApi(v);
  if (api != nullptr) break;
}
```

安全性依据：`OrtApi` 是**只追加**结构（官方 ABI 承诺），我们只访问前段成员，
因此用新头文件的定义去读老版本函数表是安全的。低于 1.12 直接报错并提示升级
（`SessionOptionsAppendExecutionProvider` 从 1.12 才有）。

### 1.3 执行提供程序探测

`provider` 支持 `auto / cpu / dml / cuda`。`auto` 按 **DML → CUDA → CPU** 顺序尝试。

- 先 DML：Windows 覆盖面最大（N/A/Intel 核显都能跑）
- 后 CUDA：只对 N 卡有效，但更快
- 名称逐个试：`DmlExecutionProvider / DML / Dml`（不同版本大小写与后缀不一致），
  失败的 append 不破坏 session options，只返回错误状态

**失败必须可见**：全部 GPU provider 都失败时回退 CPU，但要在 `LastError()` 里写明
"已回退到 CPU"。否则用户会以为自己在用 GPU——这是"怎么这么卡"的头号来源。

### 1.4 模型 I/O 探测：以模型为准，不以配置为准

初始化后查询会话的真实输入/输出维度：

- `dims[1] ∈ {1,3}` → 覆盖 `engine.channels`
- `dims[2]/dims[3] > 0` → 模型是固定尺寸，记录并强制分块尺寸等于它
- `out_dims[2] / in_dims[2]` → 真实放大倍数，覆盖 `engine.scale`

原因：配置写错（比如把 RGB 模型按单通道跑）会得到"能跑但发灰"的结果，
这是最难查的一类问题。**能让机器自己确定的，就不要让人配。**

### 1.5 分块 + 羽化

大帧整帧推理会直接打爆显存（4x 模型处理 1080p 中间张量 >10 GB）。

- 块大小 `tile_size`（默认 0 = 整帧），必须是 8 的倍数，下限 64
- 重叠 16 像素（主流 4x 模型感受野约 12—20）
- 边界处**用边缘像素钳制，不补黑边**——补黑会让模型在块边界"看到"一条黑线，
  输出出现暗边
- 重叠区做**权重累加后归一化**（线性斜坡，从 `1/(ramp)` 起，避免两端同时为 0
  导致除零）

一句话：简单切块拼接会看到方格，因为模型在块边界的感受野被截断。羽化是把
"截断"摊平成"渐变"。

### 1.6 色彩路径

`YUV420P(CPU) → RGB float(0—255) → 模型 → RGB → YUV420P`。

- 矩阵固定用 **BT.709 有限范围**。因为进入引擎前处理链已把画面转到 709；
  这里若用 601 系数，肤色会偏——**两处矩阵不一致**是"处理完颜色就是不对"的典型根因
- 单通道（`channels=1`）模型只放大亮度，色度用双线性放大：
  色度带宽需求低，不值得过模型，省 3 倍算力
- 输出色度按 2×2 盒式平均后转换，等效于一次低通，避免逐像素转再抽样产生色噪

### 1.7 实测

```
生成测试模型：python tools/gen_test_model.py testdata/models      → 0.3 KB
导出：lumen-render in.mpg out.mp4 --backend ort --model testdata/models/nearest2x.onnx --provider cpu
结果：720x480 → 1440x960，20.4 ms/帧（CPU），输出 1920x1080 正常
```

**这个模型不是产品模型**，它只是最近邻 2 倍放大，用来让"链路是否正确"可断言：
纯色画面经过"YUV→RGB→模型→RGB→YUV"往返后应当与输入一致（实测偏差 ≤2）。
真实场景请换 Real-ESRGAN / RealCUGAN / AnimeJaNai 导出的 ONNX（**opset ≤ 19**，
否则 DirectML 拒绝）。

## 2. 配置体系

### 2.1 为什么必须有

播放器是双击启动的，没有命令行；而 `--model` / `--provider` / `--runtime-dir`
这种组合每次手敲不现实。配置把这些固化成"这台机器的最佳设置"。

### 2.2 关键设计：相对路径按「配置文件所在目录」解析

不是按当前工作目录。原因：双击启动时 cwd 是 exe 目录，命令行启动时是 shell 目录，
同一份配置在两种情况下行为会不同——这类问题极难复现和解释。

### 2.3 优先级

`命令行 > 配置文件 > 内置默认值`

"平时用配置、临时改一项用参数"两种习惯都能满足。

### 2.4 容错策略

- 字段缺失 → 用默认值填（用户手改配置漏一个字段，不该导致程序起不来）
- JSON 语法错误 → **必须报错**（静默用默认值会让用户以为改动生效了）
- 数值越界 → 夹紧（crf 0—51，channels 只接受 1 或 3）

模板见 `lumen.example.json`，其中 `_xxx` 字段是写给人看的说明，解析时忽略。

## 3. 批量导出

### 3.1 为什么调子进程而不是复制代码

1. **一致性**：策略层只有一份实现，批量与单文件导出的画质必然一致。
   复制一份最容易出现"单文件没问题、批量颜色不对"。
2. **隔离**：老片容器千奇百怪，某个文件把解码器搞崩，只挂一个子进程，队列继续。
3. **可恢复**：失败文件单独重跑，不必从头。

### 3.2 串行是刻意的

超分是 GPU 密集任务，两个任务并行只会互相抢显存与算力，总吞吐不升反降，
显存不足还会直接失败。所以没有做 `--jobs`。

### 3.3 断点续跑

输出已存在且非空 → 跳过。老片批量导出动辄几小时，没有这个机制等于"中途断电全部重来"。

### 3.4 产物

- 输出：`原名_1080p.mp4`
- 日志：`logs/<原名>.log`（含 lumen-render 的完整输出，失败时是唯一线索）
- 报告：`batch_report.csv`（**带 UTF-8 BOM**，否则 Excel 打开中文乱码）

## 4. 播放器外壳

### 4.1 进程模型

```
lumen-player.exe  ──命名管道(JSON)──▶  mpv.exe
      │  UI / 策略层 / 配置               │  解码 / 渲染 / 字幕 / 音画同步
      └── --wid=<HWND> 把 mpv 画面嵌进我们的窗口
```

**许可理由**：mpv 是 GPLv2+。以独立进程 + 通用 IPC 协作，两个程序各自授权，
我们的 UI 与策略层可以闭源。这比链接 libmpv（LGPL）更干净，也省掉自建渲染管线。

**稳定性理由**：解码崩溃、驱动重置都发生在 mpv 进程里，UI 不会跟着挂。

### 4.2 IPC 客户端

- 命名管道 `\\.\pipe\lumen_<pid>`，mpv 启动后才创建，所以连接要重试（50ms 间隔）
- **单线程轮询**：`PeekNamedPipe` 读可用字节，`Sleep(1)` 循环等回复。
  刻意不用回调线程——播放器崩溃里最难查的就是跨线程碰 UI 对象
- 命令按 `request_id` 匹配；未匹配的进事件队列，由 UI 定时器取走
- 额外提供 `GetPropertyString`：`vf` 是列表类型，`get_property` 返回 JSON 数组，
  用 `get_property_string` 才能拿到可读的字符串用于回读校验

### 4.3 滤镜管理与 A/B

处理链 → mpv 滤镜的映射与导出一致（`bwdif` / `fieldmatch+decimate` / `deblock` / `hqdn3d`），
**但刻意不做色彩矩阵转换**：

> 导出处我们自己 YUV→RGB→YUV，必须显式转 601→709 并写容器标记；
> 而 mpv 是直接 YUV→RGB 上屏，它会按源标记用正确矩阵转换。
> 此时再插一个 `scale=in_color_matrix=...` 等于转换两次，画面明显偏移。
> 这是"照搬离线管线"最容易犯的错。

A/B 对比 = 挂载/移除我们自己的滤镜组（`@lumen0` …）。

### 4.4 打开文件的两段式

先 `loadfile` 让画面立刻出来，再在后台线程跑自检（6 次 ffmpeg 调用，2—10 秒），
分析完再套滤镜。反过来（先分析再播放）用户要盯着黑屏好几秒，体感像卡死。

## 5. 六个真实缺陷（都不是理论问题）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 提示"已加载但找不到 OrtGetApiBase" | `C:\windows\system32\onnxruntime.dll`（Windows ML 带来的**仿冒者**）被系统搜索路径优先命中 | 显式候选路径列表（配置目录 → exe 目录 → runtime 子目录 → 系统），逐个加载**并校验导出符号**，全部失败时把尝试过的路径列给用户 |
| 2 | 播放器窗口一闪就退 | GUI 程序的 stdin 是无效句柄，mpv 读到 EOF 当成"终端关闭"直接退出 | 加 `--no-input-terminal` |
| 3 | 按 A 切回原片，画面还是处理过的 | `vf add "@lumen:a,b,c"` 时标签**只挂在第一个滤镜**上，`vf remove @lumen` 移不掉 b、c | 逐个加独立标签 `@lumen0/1/2`，移除时逐个删 |
| 4 | 自检报 `end-file reason=error` | `--no-video` 会连视频解码一起关掉，"纯视频无音轨"的片源被判定为"无内容可播" | 改用 `--vo=null`（解码但丢弃输出） |
| 5 | 窗口拉大后画面停在左上角 | mpv 用 `--wid` 创建的子窗口不会自动跟随父窗口 | `WM_SIZE` 里 `EnumChildWindows` + `MoveWindow` |
| 6 | 生成的配置读回来全是默认值 | JSON 写出时把缩进拼进了键名（`"    backend":`），键名带空格 | 缩进写在引号外；加一条"模板往返"单元测试守住 |

第 1 条特别值得记：Windows 上"按名字找 DLL"永远有被同名文件抢先的风险。
所有**可选运行时**的加载都应该走显式路径 + 能力校验，而不是 `LoadLibrary("名字")`。

- `OnnxBackendUniformFrame`：纯色 40×24 → 80×48，逐像素与输入灰度偏差 ≤2

## 7. 未完成与风险

| 项 | 状态 | 风险 / 说明 |
|---|---|---|
| 播放器 AI 超分 | ❌ | mpv 不能跑 ONNX。要接 libaji（GPU 帧直通），其仓库**无 LICENSE 文件**，商用需书面授权 |
| DML 真机验证 | ⚠️ | 本机无 `DirectML.dll`，只验证了"失败回退 CPU"这条路径；性能未测 |
| 分屏 A/B | ❌ | 单解码器无法同时解两路；当前是切换式对比，成本/收益比不支持做分屏 |
| 真实老片调参 | ❌ | 合成素材只能验逻辑。6 类真实素材跑盲测才能定参数（见 `08`） |
| 场序像素级判定 | ❌ | 仍是元数据 + 默认 TFF；建议补 `--field-order` 手动覆盖 |
| 10bit / NV12 | ❌ | ONNX 后端明确拒绝，不做静默转换（避免画质问题难以归因） |

## 8. 对既有文档的修订建议

1. **PRD F-203「实时 1080p」** 建议拆成两条验收：
   - 播放增强（已交付：场处理 + 去块 + 降噪 + A/B）

   libaji 部分改为"待授权"。
3. **ADR-001 接缝 2 的验证标准**（换实现不改业务代码）本次已部分兑现：
   `dummy → ort` 的切换只改了一个配置字段与一个工厂分支，`core/`、`service/`
   与两个 CLI 的参数解析**零改动**。
