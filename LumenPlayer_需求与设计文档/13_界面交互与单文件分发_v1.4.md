# 界面交互与单文件分发（v1.4）

> **本轮目标**：把播放器从「只有快捷键」补成「能用的播放器」——可拖动的进度条、
> 播放/暂停按钮、文件选择、右侧信息栏、画面分辨率设置；并把发布物收敛成**一个 exe**。
> **日期**：2026-11-21
> **产物**：`dist/LumenPlayer.exe`（123.6 MB，双击即用，免安装）

---

## 一、先说结论：为什么之前「快进快退、拖动进度条没实现」

代码里其实一直有 `空格 / ← →` 的键盘处理，但用户反馈「没实现」。原因是三个问题叠在一起：

| # | 问题 | 表现 | 根因 |
|---|---|---|---|
| 1 | mpv 自带的 OSC（屏幕控制条）在嵌入模式下不可用 | 看到一条进度条，但鼠标拖不动 | `--wid` 嵌入后，鼠标事件由**父窗口**接收，mpv 的 vo 子窗口收不到；OSC 依赖 vo 窗口的鼠标事件 |
| 2 | 键盘时灵时不灵 | 点一下画面再按空格就没反应 | 点画面让焦点转到 mpv 子窗口；`--input-vo-keyboard=no` 让 mpv 不处理键盘，消息也不会冒泡到父窗口 |
| 3 | 没有可点击的入口 | 不知道能拖进度条、能暂停 | 界面上只有视频画面，所有能力都藏在快捷键里 |

结论：**在 `--wid` 嵌入方案下，必须自己画控制条**，并且把 mpv 的子窗口消息转发回主窗口。
本轮就是照这个结论重做的。

## 二、界面方案

### 2.1 布局：三块固定区域，不做浮层

```
+------------------------------+-------------------+
|                              |  正在播放          |
|          视频区               |  文件名            |
|      （mpv 子窗口）           |  时长/分辨率/编码   |
|                              |  片源分析          |
+------------------------------+  [打开文件][画质]   |
|  <<10  ⏸  10>>  音量  ——●——  时间  1.0×  ⚙  ⛶  |  [处理][场序]      |
+------------------------------+-------------------+
```

**为什么不把控制条做成「鼠标移上来才浮现」的半透明浮层**：

mpv 的子窗口铺满视频区，会盖住父窗口画在上面的任何像素。要做浮层就必须再开一个
`WS_EX_LAYERED` 顶层窗口（HUD 已经这么干了），但分层窗口做**可交互**控件意味着自己
实现整套命中测试 + 鼠标捕获 + 局部重绘，收益（省 88px 画面）远小于风险。
固定区域还带来一个好处：信息栏文字是纯 GDI 绘制，不随视频缩放变模糊。

### 2.2 为什么用纯 GDI 而不是 GDI+

只为圆角抗锯齿引入 GDI+ 的 DLL 依赖和 `GdiplusStartup/Shutdown` 管理不划算。
控制条细条只有 4px 高、圆角半径 8px，深色背景上的锯齿几乎看不见。
字体用「微软雅黑 UI + Consolas（时间数字等宽，避免秒数跳动时宽度抖动）」。

### 2.3 DPI

所有设计尺寸按 96 DPI 写死，运行时统一过 `MulDiv(v, dpi, 96)`。
漏掉这一步的典型症状：125% 缩放下按钮挤在一起、最后一行文字被裁。
本机实测环境是 120 DPI（125%），界面按 1.25 倍正确放大。

## 三、交互实现

### 3.1 键鼠消息的转发（关键前提）

mpv 的 `--wid` 子窗口会吃掉所有输入。解决方案是**子类化**它：

```cpp
s.video_proc = (WNDPROC)SetWindowLongPtrW(s.video, GWLP_WNDPROC,
                                          (LONG_PTR)VideoSubclassProc);
```

子类过程里把 `WM_LBUTTONDOWN/UP/DBLCLK/RBUTTONUP/MOUSEMOVE/MOUSEWHEEL` 用 `PostMessage`
转发给主窗口，其余交给原窗口过程。

- 坐标不需要转换：视频区永远从 `(0,0)` 开始，子窗口客户区坐标 == 主窗口客户区坐标
- 同时把 mpv 的绑定全关掉（`--osc=no --input-default-bindings=no --input-vo-keyboard=no`），
  否则会出现「一次点击两边都响应」的双触发

### 3.2 进度条拖动

```
鼠标按下 → 命中 kHitSeekBar → dragging_seek = true, 记录 drag_pos, SetCapture
鼠标移动 → drag_pos = (x - track.x) / track.w * duration，只重画，不发 seek
鼠标松开 → SeekAbsolute(drag_pos)，ReleaseCapture
```

三个细节：

1. **拖动中不跟随真实播放位置**：否则每 250ms 的属性刷新会把滑块「拽回去」，手感像卡死。
2. **松手才 seek**：拖动过程中连续 seek 会让 mpv 反复解码，画面卡顿。
3. **`absolute+exact`**：默认 seek 会吸附到关键帧，用户拖到 12.3 秒却停在 9 秒，
   体感就是「拖不准」。代价是稍微慢一点，但准确性更重要。

实测：拖到轨道 56.6% 处 → UI 计算 16.99 秒 → mpv 实际 `time-pos = 16.984`，误差 6ms。

### 3.3 单击暂停 / 双击全屏

Windows 会先发 `WM_LBUTTONDOWN/UP`，再发 `WM_LBUTTONDBLCLK`。如果直接响应单击，
双击会先暂停一次再全屏，观感是「画面顿一下才放大」。

做法：单击不立刻执行，而是 `SetTimer(GetDoubleClickTime()/2)` 延迟 ~250ms；
双击消息到达时 `KillTimer` 取消暂停。代价是单击暂停有 0.25 秒延迟，符合播放器惯例。

### 3.4 播放/暂停：为什么放弃 `cycle pause`

最初用 mpv 的 `cycle pause` 命令，实测**点击后没有反应**。原因是 `cycle` 依赖 mpv
内部的当前值，而我们的本地缓存与它可能不同步（刚 seek 完属性还没刷新）。

改为显式置位：

```cpp
const bool next = !s.stats.paused;
s.ipc.SetProperty("pause", next ? "yes" : "no");
s.stats.paused = next;   // 立即更新本地状态并重画，不等下一个 250ms 采样
```

好处是可预测 + 界面即时反馈，不用等定时器刷新。

### 3.5 片尾的「播放」语义

`keep-open=yes` 时播放结束会停在最后一帧。此时按空格如果只是「解暂停」，画面不会动，
用户会以为卡死。所以 `eof` 状态下按播放 = 跳到 0 秒 + 解除暂停（重播），
按钮图标也换成 ↻。

判断要收紧：`eof-reached` 在「视频流比音频短」的老片上会提前为真（实测 32/40 秒）。
条件改为 `eof_reached && pos >= dur - 3`，否则视为暂停。

## 四、右侧信息栏

### 4.1 数据来源

| 显示项 | 来源 | 备注 |
|---|---|---|
| 文件名 | mpv `media-title` → 回退文件名 | 有的片内嵌标题比文件名友好 |
| 时长 | `duration` | |
| 分辨率 | `video-params/w,h` | 未解码时回退自检报告的宽高 |
| 画面比例 | `video-params/aspect` → 映射为 4:3 / 16:9 / 3:2 … | 避免直接显示 1.778 |
| 帧率 | `container-fps`（不是 `estimated-vf-fps`） | 后者是「当前输出帧率」，反交错时会在 23.976/29.97 之间跳，用户会以为坏了 |
| 视频/音频编码 | `video-codec` / `audio-codec` → 缩短映射 | mpv 返回 `H.264 / AVC / MPEG-4 AVC / MPEG-4 part 10 (High)`，需截成 `H.264（High）` |
| 码率 | `video-bitrate + audio-bitrate`，失败用 `file-size*8/duration` | TS/老 AVI 常不报码率 |
| 硬件解码 | `hwdec-current` → 中文 | `no` 要说成「软件解码」而不是把 `no` 打到屏幕上 |
| 片源/处理/色彩/超分 | 自检报告 + 处理链 | 本产品真正的差异化信息 |

采样分两档：位置/时长/暂停/音量每 250ms（进度条要跟手），
帧率/分辨率/编码/码率每 500ms（这些值不会跳，读太勤纯浪费 IPC）。

### 4.2 空间自适应

窗口矮（1366×768 笔记本）时不能再硬塞 12 行。策略是三档：

1. 空间够 → 行高 23px，12 行全显示
2. 勉强够 → 行高压到 20px，仍显示 12 行
3. 不够 → 只显示 8 行基本信息（时长/分辨率/比例/帧率/编码/码率/硬解），
   收起「片源分析」分组

底部按钮区是**硬预算**，从下往上先排好，信息区只用剩下的空间——
保证无论窗口多矮，「打开文件」永远点得到。

## 五、画面设置：三层语义

用户说的「设置分辨率」其实对应三件不同的事，菜单里分成三组，避免歧义：

| 组 | 选项 | 实现 |
|---|---|---|
| 窗口尺寸 | 100% / 150% / 200% / 最大化 | 按视频显示尺寸（`vh × aspect`）算出客户区，加边框、侧栏、控制条后 `SetWindowPos` |
| 画面比例 | 适应 / 拉伸 / 裁剪 / 原始像素 | mpv `keepaspect` + `panscan` + `video-unscaled` 三个属性组合 |
| 输出分辨率 | 原生 / 720p / 1080p / 1440p / 2160p | 挂 `scale=w=-2:h=1080:flags=lanczos` 滤镜 |

### 输出分辨率必须和场处理一起重建

mpv 的 `vf` 是**有序链**，`vf add` 永远追加到末尾。如果单独在别处挂缩放，
之后切 A/B（先删 `@lumen*` 再重新加场处理）就会变成「缩放 → 反交错」：
交错线先被放大两倍再去做场匹配，画面反而更差。

所以 `ApplyChain()` 每次都按「场处理 → 缩放」的顺序一次性拼好，标签分开
（`@lumen0..3` 是场处理，`@lumenout` 是缩放），A/B 时只删前者。

`w=-2` 让宽度按比例自动算，避免 4:3 片源被拉成 16:9。实测 720×480 → `VO: 1620x1080`
（保持 3:2），滤镜语法正确。

**注意**：这不是 AI 超分。HUD 和侧栏都明确写「超分 未接入实时路径」，
不能让用户以为选了 1080p 就等于做了超分。

## 六、单文件分发

### 6.1 问题

上一版发布包里有 4 个 exe（player / probe / render / batch）+ 一个 mpv 目录：

- 用户不知道该点哪个
- 有人把 `mpv.exe` 当成本程序本体去双击（然后看到 mpv 自己的界面，以为我们套壳）
- 「压缩包 64MB，解压到哪都能跑」听起来好，实际上多一步就多一半人放弃

### 6.2 方案：把 mpv 嵌进 exe

```
LumenPlayer.exe (124MB)
├── 程序代码            ~3 MB
└── RCDATA 资源
    ├── 101 → mpv.exe            116 MB
    └── 102 → d3dcompiler_43.dll   4 MB
```

首次运行释放到 `%LOCALAPPDATA%\LumenPlayer\`，之后按文件大小校验复用。

几个设计决定：

| 决定 | 理由 |
|---|---|
| 释放到 `%LOCALAPPDATA%` 而不是 exe 同目录 | 程序可能被放进 Program Files（无写权限）；而且「单文件」旁边突然长出一堆文件会让用户以为装坏了 |
| 先写 `.tmp` 再 `MoveFileEx` 原子替换 | 上一个实例可能还在跑，直接覆盖会失败；半截文件比没有更糟——下次启动会把它当成「已释放」 |
| 同目录有 `mpv.exe` 时优先用用户的 | 高级用户可以直接替换 mpv 版本；开发时的 build 目录布局也继续可用 |
| 不嵌 onnxruntime/DirectML | 那是离线导出（lumen-render）用的 32MB，播放路径完全用不到 |

### 6.3 为什么是 124MB

mpv 的 Windows 静态构建本身就是 121MB（解码器、滤镜、字幕、渲染器全在里面）。
这是「单文件 + 零安装」的必然代价。试过 UPX，能压到 ~45MB，但启动要解压 120MB，
而且极易被杀毒软件误报，不值得。

### 6.4 许可

mpv 是 GPLv2+，本项目以**独立进程 + JSON IPC** 调用，未链接其代码（ADR-001 的进程边界）。
单文件发布后没有随附的 `THIRD-PARTY-NOTICES.txt`，所以许可信息放进程序内：
右键 → 关于 LumenPlayer，显示 mpv 版本、许可、源码地址、内嵌运行时位置。

### 6.5 构建

```bash
python tools/build_single.py              # dist/LumenPlayer.exe（124MB）
python tools/build_single.py --no-embed   # 只编译（3MB，开发调试用）
```

旧的 `tools/make_release.py`（打 4 个 exe 的 zip）已删除，避免两套打包逻辑并存。

## 七、过程中踩到的坑

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 拖动进度条没反应 | 测试工具没声明 DPI 感知，`SendMessage` 的坐标被系统按 125% 又缩放了一次，点到视频区去了 | 工具加 `SetProcessDPIAware()`（产品本身无此问题） |
| 2 | 点播放按钮不生效 | `cycle pause` 依赖 mpv 内部状态，与本地缓存不同步 | 改显式 `SetProperty("pause", ...)` |
| 3 | 点齿轮没反应 | `TrackPopupMenu` 要求 owner 是**前台窗口**，否则立即返回 0 | 调用前 `SetForegroundWindow(hwnd)` |
| 4 | 菜单向下展开盖住控制条 | 默认 `TPM_TOPALIGN` | 改 `TPM_BOTTOMALIGN` 向上展开，并贴着鼠标位置 |
| 5 | 32/40 秒就显示「播放结束」 | 视频流比音频短的老片，`eof-reached` 提前为真 | 加 `pos >= dur - 3` 条件 |
| 6 | 侧栏「逐行 · 逐行（自动）」自我重复 | 片源节奏与场序都映射成「逐行」 | 前缀相同时合并成一项 |
| 7 | `RT_RCDATA` / `IDC_HAND` 编译错误 | 这两个宏在非 Unicode 目标下展开成 ANSI 版本 | 用 `MAKEINTRESOURCEW(10)` / 数字 32649 |
| 8 | 侧栏在矮窗口下内容被裁 | 行高写死 24px，底部按钮区又占满 | 三档自适应 + 按钮区硬预算 |
