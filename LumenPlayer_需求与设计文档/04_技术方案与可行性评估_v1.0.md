# LumenPlayer 技术方案与可行性评估

| 项目 | 内容 |
|------|------|
| 版本 | v1.0（选型建议，未落地） |
| 日期 | 2026-11-20 |
| 结论先行 | **可行，但必须先做"推理性能探针"再动手写播放器。** 播放器是已解决问题，实时超分才是未知数 |

---

## 1. 可行性结论（TL;DR）

| 判断项 | 结论 | 依据 |
|--------|------|------|
| 480p/720p → 1080p 实时超分在消费级 GPU 上能否跑到 24/30fps？ | **能，但分档严重**。中端独显（RTX 3060 级）跑轻量模型可满足；核显只能跑 shader 类算法 | 同类开源方案（mpv + Real-ESRGAN Compact ONNX，TensorRT/DirectML）已实现 1080p→4K 实时，本项目是 480p→1080p，像素量低得多，压力更小 |
| 是否有成熟可参考的工程路径？ | 有。**"自持渲染器 + ONNX 推理接入视频管线"** 已被验证为可行架构（mpv 分支类项目即此路线） | 参考实现证明：必须拥有渲染器，插件式挂载会与播放器争抢帧 |
| "变蓝光"能否达到？ | **不能等于，但观感可显著提升**。需把目标定义为"无伪影 + 锐度提升 ≥25% + 时序稳定" | 超分无法恢复未被记录的信息；35mm 胶片扫描才是真蓝光来源 |
| 跨平台复用率？ | 核心引擎（解码/管线/推理调度/策略）可 100% 复用；渲染层与推理后端需各平台实现，UI 全重写 | 见 §6 |
| 最大技术风险？ | ①实时预算不够导致掉帧 ②鸿蒙推理链路成熟度 ③老片隔行/颗粒处理不当反而更丑 | 见 §8 |

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  UI 层（各平台原生：Win32/Qt 或 WinUI3 │ Android Compose │ ArkTS）│
├─────────────────────────────────────────────────────────────┤
│  应用服务层：播放会话 · 片源自检 · 策略引擎 · 导出队列 · 配置/缓存  │
├─────────────────────────────────────────────────────────────┤
│  核心引擎（C++ 单一代码库，跨平台）                              │
│  ┌──────────┬──────────┬──────────┬──────────┬─────────────┐ │
│  │ Demux/   │ 预处理链  │ 超分推理  │ 后处理链  │ 帧调度/同步  │ │
│  │ Decode   │ PreProc  │ ISRBackend│ PostProc │ Clock/Pacing│ │
│  └──────────┴──────────┴──────────┴──────────┴─────────────┘ │
├─────────────────────────────────────────────────────────────┤
│  平台抽象层（PAL）：IRenderer │ IDecoder │ IInferenceBackend   │
│                     IAudioOut │ IFileSys │ IPowerMonitor       │
├─────────────────────────────────────────────────────────────┤
│  Windows: D3D11/12 · D3D11VA/DXVA · WASAPI · ONNX(TensorRT/DML)│
│  Android: Vulkan/GLES · MediaCodec · AAudio · ORT(NNAPI/QNN)  │
│  HarmonyOS: Vulkan/GLES(XComponent) · AVCodec · OHAudio · TBD  │
└─────────────────────────────────────────────────────────────┘
```

**关键架构决策：自持渲染器（own the renderer）**。不采用"插件挂进第三方播放器"的方案，因为超分帧必须直接进 swapchain，中间过一道插件边界会引入拷贝与同步开销，且无法控制丢帧策略。

## 3. 播放核心选型

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **A. libmpv 嵌入 + 自定义 video filter 注入** | 播放/字幕/同步/格式兼容全部现成，MVP 最快（省 3—6 个月） | 注入 ONNX 推理需改 mpv 源码或用 VapourSynth 桥（引入 Python 依赖）；帧调度被 mpv 掌控，降级策略受限 | **推荐用于 M1 快速验证体验**，不作为终态 |
| **B. 自研：libav* 解码 + 自建渲染器 + 推理调度** | 完全掌控帧节奏、丢帧、降级、色彩管理；性能最优；跨平台干净 | 工作量大（同步/seek/字幕/音轨全要自己写） | **推荐作为终态架构**（M2 起迁移） |
| C. 基于 VLC/libVLC | 格式兼容强 | 渲染管线封闭，实时推理几乎无法插入 | 排除 |
| D. 基于 Electron/Web 技术 | UI 快 | 无法做 GPU 级实时推理与零拷贝 | 排除 |

**建议路线（已于 2026-11-20 开源调研后修订，详见《06_开源项目调研与复用方案》）**：
- **A 升级为首选内核**：libmpv（LGPL 构建）不再是"过渡方案"，而是三条复用路线中的共同地基。理由：mpv 已解决字幕/同步/seek/格式这四类最耗时的已知工程，重写它没有产品价值。
- **B 降级为路线 C 的备选**：仅在"必须完全自研"（严格合规或要绕开 LGPL）时才走。
- 真正的自研投入应集中在**策略层**：片源自检、场处理、色域/画幅、颗粒保留、降级决策 —— 这正是现有开源项目的空白区（见 06 §3）。

> 许可提示：libmpv 需以 **LGPLv2.1+** 配置构建（关闭 GPL-only 组件）方可闭源分发；商用前须法务确认。

## 4. 处理管线设计（本产品的真正壁垒）

### 4.1 五段式管线

```
解码帧(YUV)
  ↓ ① 场处理：IVTC / 运动自适应去隔行（必须先做，否则超分会放大梳齿）
  ↓ ② 几何：黑边检测裁切 → SAR/DAR 归一 → 目标画布映射
  ↓ ③ 色彩：BT.601/709 判定 → TV/PC range 纠正 → 转线性或保持 YUV
  ↓ ④ 修复前置：轻去块（deblocking）/ 轻去噪（按 DamageProfile 强度）
  ↓ ⑤ 超分推理（模型链，2x） → 后处理：降采样到 1080p / 颗粒回注 / 轻锐化
  ↓ 呈现（swapchain），帧调度按音频时钟对齐
```

### 4.2 为什么"必须先做场处理"

90—00 年代电视剧绝大多数是 **480i/576i 隔行**或**胶转磁（3:2 pulldown）**。若直接把隔行帧送进超分模型：
- 模型会把每场的梳齿当作"细节"放大 → 输出锯齿更明显；
- 时间上两场属于不同时刻 → 时序不一致 → 画面"抖"。

**规则**：`isInterlaced == true` 时，超分必须排在 IVTC/去隔行之后，且推理输入必须是完整帧。

### 4.3 为什么"去噪要保守"

AI 超分模型对噪声敏感：噪声会被当成纹理强化，产生"油画感/蠕动的颗粒"。但去噪过度会抹平胶片颗粒 → "蜡像脸"。
**策略**：
- 去噪只针对**压缩损伤**（块效应、蚊噪），不针对胶片颗粒；
- 颗粒在超分后**回注**（从原帧提取高频残差，按比例叠加），这是保住"胶片感"的关键手法；
- 颗粒保留强度默认 60—80，不做 100% 也不做 0%。

### 4.4 模型链（建议）

| 片源类型 | 模型链 | 说明 |
|----------|--------|------|
| 实景老电影 / 老剧（默认） | 轻量 Real-ESRGAN 变体（Compact 级，2x）→ 降采样至 1080p → 颗粒回注 | 轻量模型是实时前提；大模型（x4plus 级）只用于离线导出 |
| 动画（赛璐璐） | 动画专用链：着色器类实时算法（Anime4K 类，MIT）或动画超分模型 | 通用实景模型会给平涂区加假纹理 |
| 极低码率 / VCD 级 | 强去块 + 轻超分 + 抑制锐化 | 强行锐化只会放大块效应 |
| 无 GPU / 核显 | 纯着色器路径：Lanczos/FSR 类上采样 + CAS 锐化 | 无 AI 但明显优于默认双线性 |
| 源 ≥1080p | 旁路（仅正确缩放与色彩） | 避免过度处理 |

> 许可：Real-ESRGAN（BSD-3）、Real-CUGAN（MIT）、Anime4K（MIT）可用；**Video2X 为 AGPL-3.0，禁止链接进主程序**。

### 4.5 推理后端抽象

```cpp
class ISRBackend {          // 每个平台各自实现
  virtual bool Init(const ModelSpec&, const DevicePref&) = 0;
  virtual bool Warmup();                                  // 可异步，带进度
  virtual bool Infer(const Frame& in, Frame& out) = 0;     // 同步，可切片
  virtual PerfStats Stats() const = 0;                     // ms/帧、显存
  virtual void OnDeviceLost();                             // TDR/驱动重置自愈
};
```

| 平台 | 主后端 | 备后端 | 兜底 |
|------|--------|--------|------|
| Windows | TensorRT（N 卡，最快） | ONNX Runtime + DirectML（A 卡/Intel） | CPU（仅预览/导出用）/ 着色器 |
| Android | ORT + NNAPI / QNN（骁龙） | NCNN-Vulkan | 着色器（GLES/Vulkan） |
| HarmonyOS | 待验证（CANN/OM 模型 或 NCNN-Vulkan） | 同左 | 着色器 |

实测参考：同类模型中 TensorRT（FP16）相对 ONNX Runtime 通用路径约有 **2—2.5 倍**吞吐优势，DirectML 路径通常比 TensorRT 慢 30%—60%。这直接决定档位划分。

**现成引擎可对接（2026-11-20 调研补充）**：`the-database/animejanai-inference` 的 **libaji** 提供了与此抽象几乎同构的 C ABI（`aji.h`：GPU 常驻 YUV 帧进、超分帧出，含 chain / RIFE / temporal 模型，后端可选 TensorRT / TensorRT-RTX / DirectML），并可运行时动态加载，**无需自己写 D3D11↔CUDA 互操作**。两个硬约束：①DirectML 路径 ONNX 须导出到 **opset ≤19**（缺 opset-20 `Gelu` 会回落 CPU）；②首次 TensorRT 加载需建 engine（分钟级，缓存键含模型/尺寸/GPU/TRT 版本）。许可见 06 文档 §7（该仓库无 LICENSE 文件，商用须书面授权）。

## 5. 性能预算（必须算清楚再写代码）

### 5.1 单帧预算

| 片源帧率 | 每帧可用时间 | 留 30% 余量后的推理预算 |
|----------|--------------|------------------------|
| 23.976 / 24 fps | 41.7 ms | **≤ 29 ms** |
| 25 fps | 40.0 ms | ≤ 28 ms |
| 29.97 / 30 fps | 33.4 ms | ≤ 23 ms |

> 注意：30fps 片源才是紧的那一档。老剧多为 25/29.97fps，**不能用 24fps 的预算做设计**。

### 5.2 像素量估算

- 480×360 → 960×720（2x）：0.69 M 像素/帧
- 720×480 → 1440×960（2x）：1.38 M 像素/帧
- 参考：1080p→4K（2x）是 8.3 M 像素/帧，已被证明可在中高端卡实时

**结论**：本项目像素量只有"1080p→4K"的 **1/6 — 1/12**，实时可行性显著更高。这是重要的乐观依据。

### 5.3 非模型开销（易被低估）

| 项 | 估算 | 备注 |
|----|------|------|
| 硬件解码 | 1—3 ms | 硬解路径，可忽略但需独立队列 |
| 去隔行（GPU shader） | 1—2 ms | 仅隔行片源 |
| 色彩转换 + 缩放 | 1—2 ms | 用 compute shader，勿走 CPU |
| 显存↔显存拷贝 | 0.5—2 ms | **零拷贝是硬要求**，D3D11 纹理直接喂 ORT（DML EP 支持 D3D12 资源） |
| 呈现/垂直同步 | 0—16 ms | 帧节奏控制，不占算力但影响掉帧观感 |

**工程红线**：解码输出必须是 GPU 纹理，全链路不得回落到 CPU（一次 1080p 回读 = 数 ms + 带宽灾难）。

## 6. 跨平台策略

| 层 | Windows | Android | HarmonyOS NEXT |
|----|---------|---------|----------------|
| UI | Qt6 / WinUI3（建议 Qt6，便于后续复用思路） | Jetpack Compose | ArkTS + ArkUI |
| 渲染 | D3D11（成熟）/ D3D12 | Vulkan（GLES 兜底） | XComponent + native window，Vulkan/GLES |
| 解码 | D3D11VA / DXVA2 | MediaCodec（Surface 直出） | AVCodec（系统媒体能力） |
| 音频 | WASAPI | AAudio / Oboe | OHAudio |
| 推理 | TensorRT / DirectML | NNAPI / QNN / NCNN-Vulkan | **待 POC**（CANN/OM 或 NCNN-Vulkan） |
| 打包 | MSI/EXE（含模型可选） | AAB/APK | HAP |

**复用率预估**：核心引擎（管线、策略、自检、调度、导出）≈70%—80% 代码可复用；渲染层与推理后端各平台重写（约占 20%—30%）。

**鸿蒙最大不确定性**：
1. HarmonyOS NEXT 不再兼容 APK，须原生重写 UI；
2. 推理链路：ONNX 模型能否直接跑、算子覆盖率、GPU/NPU 加速可用性均需实测；
3. 若推理不可用，保底方案是**着色器超分**（Anime4K 类算法可在 GLES/Vulkan 上跑），效果弱于 AI 但可用。

→ **结论：鸿蒙必须在 M2 阶段就做一个"单帧推理能否跑通"的最小 POC，不要等 UI 做完才发现引擎上不去。**

## 7. 关键技术难点与对策

| # | 难点 | 对策 |
|---|------|------|
| T1 | 首次 TensorRT engine 构建耗时数十秒 | 预置通用 engine + 后台异步构建 + 明确进度 UI + 构建期用 DirectML/着色器临时兜底 |
| T2 | TDR（Windows 2s 超时）导致驱动重置、整屏黑闪 | 推理切片（tile）；单帧耗时限流；捕获 `DXGI_ERROR_DEVICE_REMOVED` 后重建全部 GPU 资源 |
| T3 | 解码与推理抢 GPU 导致双输 | 双队列 + 优先级；推理用低优先级 compute queue；显存预留；必要时降档 |
| T4 | seek 时大量帧突发导致瞬间超预算 | seek 后进入"快速预览模式"（着色器上采样），稳定后 200—500ms 内切回 AI |
| T5 | 24fps 内容在 60Hz 屏上的抖动（judder）与超分无关但被误认为画质问题 | 帧节奏控制：优先匹配刷新率（VRR/切 48/72/120Hz），或做 3:2 均匀化；HUD 显示实际呈现节奏 |
| T6 | 色域错标导致整体偏色 | 严格按容器/编码标记判定，未标记 SD 默认 BT.601；提供手动覆盖 |
| T7 | 长时播放显存/句柄泄漏 | 对象池 + RAII + 每 10 分钟自检资源计数；CI 跑 3h 压测 |
| T8 | 模型体积与首装体验 | 基础档随包（数十 MB），高档按需下载 + 哈希校验 |

## 9. POC 计划（写播放器之前必须完成的 3 个验证）

| POC | 目标 | 通过标准 | 预估工作量 |
|-----|------|----------|------------|
| **POC-0 推理探针** | 用真实 480i/720p 老片片段，测各档模型在目标 GPU 上的 ms/帧 | 中端独显在 30fps 片源下 ≤23ms；核显 shader 路径 ≤10ms | 3—5 天 |
| **POC-1 画质对照** | 6 类标准样本跑"原片 vs 增强"盲测 | ≥5 人判定无蜡像脸/无振铃；锐度提升可测 | 3 天 |
| **POC-2 跨平台引擎** | 同一 C++ 推理模块在 Android 上跑通；鸿蒙单帧推理最小验证 | 至少一个平台非 Windows 跑通 2x 推理 | 5—8 天 |

**POC-0 是第一道闸门**：如果中端卡跑不到预算，整个产品定位必须改为"离线重制为主、实时为辅"，架构与 PRD 都要改。**不要在 POC-0 通过前写播放器 UI。**
