## 三个必须先知道的结论

**1. "1080p 蓝光高清"是承诺不了的。**
480p 上采样不可能还原从未被记录的信息。真蓝光来自 35mm 胶片扫描。产品能兑现的是：无新增伪影、锐度提升 ≥25%、时序稳定、颗粒保留。对外口径建议改为「蓝光级观感增强」，否则必然出现"根本没变蓝光"的差评。

**2. 老片的头号杀手不是分辨率低，是隔行和胶转磁。**
90—00 年代剧集多是 480i/576i 隔行或 3:2 pulldown。直接把隔行帧送进超分模型，会把梳齿当细节放大 —— 结果是"放大的糊 + 放大的锯齿"。所以「片源自检 + 先做场处理」必须是 P0，不是后期优化。

**3. 开发顺序得倒过来：先证明跑得动，再做播放器。**
播放器是已知工程（现成方案很多），实时超分是未知数。必须先做 POC-0「推理性能探针」，用真实老片片段在目标显卡上测出 ms/帧。**这一关不过，整个产品定位要改成"离线重制为主"，PRD 得重写。**

## 可行性速览

| 问题 | 答案 |
|------|------|
| 480p→1080p 实时超分能跑到 24/30fps 吗？ | 中端独显（RTX 3060 级）跑轻量模型可以；核显只能跑着色器类算法 |
| 为什么乐观？ | 本项目像素量只有"1080p→4K 实时"的 1/6～1/12，已被开源方案验证可行 |
| 单帧预算 | 30fps 片源最紧：33ms，留 30% 余量 → 推理必须 ≤23ms |
| 有没有现成路径可参考？ | 有。自持渲染器 + ONNX 推理接入视频管线（TensorRT / DirectML）已被验证 |
| 跨平台复用率 | 核心引擎 70%—80% 可复用，UI 与渲染层各平台重写 |
| 最大不确定性 | 鸿蒙推理链路成熟度 —— 必须在 M2 就做单帧 POC，别等 UI 做完 |

## 开源复用的关键结论（详见 06）

**技术上能省 60%—80% 的量，但许可上有三道锁。**

- 头号发现：`the-database` 的 **libaji（推理引擎）+ vf_animejanai（mpv 滤镜）** 几乎就是我们要的架构 —— GPU 常驻 YUV 帧进、超分帧出，TensorRT / DirectML 双后端，还自带 ms/帧 基准工具（1080p→4K 约 3.8ms @ RTX 5090）。
- 但：`mpv-AnimeJaNai` 是 **CC BY-NC-SA 4.0（禁止商用）**；底层 mpv 是 **GPL**；`libaji` **没有 LICENSE 文件**（法律上=保留所有权利，需作者书面授权）。
- 所以要先选边：**A 开源最快（2—4 周）／ B 自研外壳+复用引擎可闭源（8—14 周）／ C 全自研（5—8 个月）**。
- 推荐路径：**先 A 后 B** —— 用 2 周把真正的差异化（片源自检 + 老片策略 + 颗粒保留 + A/B 对比）做出来验证，这套代码与许可无关，可原样搬进 B。

## 里程碑

```
M0 可行性验证(2-3周) → M1 体验原型(4-6周) → M2 核心引擎(8-12周)
   → M3 Windows公测(6-8周) → M4 Android(8-10周) → M5 鸿蒙(6-10周)
```

每个里程碑有硬性"过闸标准"，未过闸不进下一阶段。M0 是阻塞闸门。

## 合规红线（已在文档中固化）

- 播放器**不提供、不索引、不下载任何影视资源**，不实现 DRM 解密
- 仅播放用户本地文件，**永不修改源文件**（除用户显式导出）
- 主程序**禁止**链接 AGPL 组件（如 Video2X）
- FFmpeg 必须 LGPL 配置，**禁止** GPL 编码器（libx264/libx265），导出走硬件编码
- 一期**零网络请求**
